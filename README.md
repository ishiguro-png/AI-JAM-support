# AI JAM サポート管理システム

admin.torimato.jp の契約管理システムから、サポートプラン対象（5アカウント以上 / 10アカウント以上 / 30アカウント以上）の契約先を抽出・管理するための社内ツールです。

- torimato からエクスポートしたCSVを取り込み、契約行の数量を会社単位で合算し、サポートプラン（5+ / 10+ / 30+）を自動判定
  （同一会社の「月契約」「年契約」等の複数行にも対応。「契約状態」列が「契約中」の行だけをカウントし、契約開始日・終了日は表示用にのみ保持）
- 契約先ごとにサポートメールをGmail経由で送信し、送信内容・送信結果を自動で対応履歴に記録
- 電話・訪問・メモなどメール以外の対応も手動で記録でき、誰が対応しても同じ画面で経緯が追える
- ログイン機能は設けず、社内アクセスのみを前提とした簡易システムです（担当者名は入力式で記録）

## 技術構成

- Next.js 14 (App Router) + TypeScript
- Prisma + SQLite（ファイルDB、`prisma/dev.db`）
- Tailwind CSS
- Nodemailer（Gmail SMTP、アプリパスワード方式）
- PapaParse（CSVパース、列マッピングはブラウザ上で実施）

## セットアップ

```bash
npm install
cp .env.example .env
# .env を編集: GMAIL_USER / GMAIL_APP_PASSWORD を設定
npx prisma migrate dev   # リポジトリに含まれるマイグレーションを適用（新規追加は不要なので --name は付けない）
npm run seed   # 担当者・メールテンプレートの初期データ投入（任意）
npm run dev
```

http://localhost:3000 で起動します。

### Gmail送信の設定

サポートメールは実際にGmail経由で送信されます。送信専用のGoogleアカウント（または担当部署のアカウント）で以下を行ってください。

1. Googleアカウントで2段階認証を有効化
2. https://myaccount.google.com/apppasswords でアプリパスワードを発行
3. `.env` の `GMAIL_USER` に送信元アドレス、`GMAIL_APP_PASSWORD` に発行されたアプリパスワードを設定

## 使い方

1. **CSVインポート**（`/contracts/import`）: torimatoからエクスポートしたCSVをアップロードし、列とシステム項目（会社名・会社ID・数量・契約状態・契約種別・契約開始日・契約終了日・商品名・金額・
   申込日・代理店・請求方法・キー発行状況・契約IDなど）を対応付けて取り込みます。torimatoの実際の列名（サービス名・契約タイプ・金額(税込)・契約期間（開始/終了）等）は
   自動マッピングされ、マッピングされなかった列は「未使用列」として一覧表示されます（詳細は下記「自動マッピングされる列名」を参照）。
   会社名・数量・契約状態は集計に必須のためバリデーションされます。それ以外の項目は任意です。
   torimatoのCSVは同一会社について「月契約」「年契約」が別行になっていることがありますが、1行 = 1つの契約明細として取り込まれ、会社単位でまとめられます。
   会社の同一性は「会社ID」があればそれを優先し、無ければ会社名で判定します。会社名だけの判定は全角/半角スペースなどの表記ゆれで
   同じ会社が別の契約先として重複登録される恐れがあるため、torimato側に顧客IDなど会社単位で一意な列があれば必ずマッピングしてください。
   **「最新のCSVが現在の契約状態の正」という方針のため、会社ごとの契約明細（`ContractLine`）はインポートのたびに今回のCSVの内容で完全に
   置き換わります**（詳細は下記「CSVインポート方式」を参照）。連絡先などContract側の情報は、今回のCSVに値がある項目だけ上書き更新されます。
2. **契約一覧**（`/contracts`）: サポートプラン（5+/10+/30+）やステータスで絞り込み、対象契約先を確認できます。
3. **契約詳細**（`/contracts/[id]`）: 契約先ごとに現在のアカウント数の内訳（契約明細一覧: 商品名・数量・金額・契約タイプ・契約状態・契約開始日・契約終了日・申込日・代理店・請求方法・
   キー発行状況。各行の契約状態が「契約中」なら集計対象、それ以外は対象外）、サポートメールの送信、対応履歴（電話・訪問・メモ等）の記録・閲覧ができます。
4. **メールテンプレート**（`/templates`）: プラン別の定型連絡文をあらかじめ登録し、送信フォームから呼び出せます。
5. **担当者管理**（`/staff`）: 対応記録・メール送信時に選択する担当者名を管理します。

## データモデル

- `Contract`: 契約先（会社）情報。会社名・会社ID（任意、torimatoの顧客IDなど）・連絡先・ステータス。アカウント数とサポートプランはここには保存せず、`ContractLine`から都度集計する
- `ContractLine`: 契約明細（torimatoの1行 = 月契約/年契約などの単位）。torimatoのCSVに含まれる主要項目をできるだけ網羅的に保持する。
  - `contractType`（契約種別）・`contractStatus`（契約状態）・`quantity`（数量）: 集計・判定に使用
  - `productName`（商品名/サービス名）・`amount`（金額）・`startDate`/`endDate`（契約期間）: 表示用・`npm run verify`の整合性チェック用
  - `applicationDate`（申込日）・`agencyName`（代理店）・`billingMethod`（請求方法）・`keyIssuedStatus`（キー発行状況）: 表示用の参考情報
  - CSVの値は基本的にそのまま保持するが、`keyIssuedStatus`のみ「済」「未」等の表記ゆれをできるだけ吸収して正規化する
    （`src/lib/contractLines.ts`の`normalizeKeyIssuedStatus`。判定できない場合は元の文字列をそのまま保持する）
  - **CSVインポートのたびに、その会社の行は全件削除して今回のCSVの内容で作り直される**（過去のCSVとの突合・upsertは行わない。
    詳細は下記「CSVインポート方式」を参照）
- `SupportLog`: 対応履歴（メール送信ログを含む。種別・担当者・内容・日時）。`Contract`に紐づき、CSV再インポートで`ContractLine`が
  置き換わっても削除されない
- `EmailTemplate`: プラン別メールテンプレート
- `Staff`: 対応記録用の担当者名リスト
- `ImportBatch`: CSVインポートの実行履歴（インポート日時・ファイル名・CSV行数・会社数・成功件数・エラー件数）。
  `ContractLine`自体は最新CSVの内容に置き換わってしまうため、過去に何を・いつ・何件取り込んだかはこのテーブルにのみ残る

### アカウント数の集計ロジック

会社ごとに、**`ContractLine.contractStatus`（契約状態）が「契約中」の行のみ**を対象に数量を合算し、
その合計値でサポートプラン（5+/10+/30+）を判定します。「契約前」「解約」の行はカウントに含みません。

torimatoのCSVに入っている契約開始日・契約終了日は、無料期間や契約切り替えの都合で実際の契約状態と
ずれることがあるため、**集計判定には一切使用せず**、契約詳細画面に表示する参考情報としてのみ保持します。
このため`ContractLine.startDate`/`endDate`は任意項目（無くても取り込み可能）です。

集計はページ表示のたびに計算されるため、CSVの契約状態を更新して再インポートすれば、
即座に一覧・ダッシュボードのアカウント数・プラン判定に反映されます。

### `Contract.status` と `ContractLine.contractStatus` は別物

- `Contract.status`（稼働中/一時停止/解約）: このアプリ内だけで管理する対応ステータス。契約詳細画面から手動で変更する。**CSVインポートで書き込まれることはない**
- `ContractLine.contractStatus`（契約中/契約前/解約）: torimatoのCSVの「契約状態」列そのもの。契約明細（行）ごとに保持し、アカウント数集計にのみ使う

会社は複数の契約明細を持ちうる（例: 月契約=契約中、年契約=契約前）ため、契約一覧画面では
個々の契約明細のcontractStatusをそのまま会社の行に表示せず、「有効N / 全M件」という
会社単位の集約表示にしています。契約状態の内訳は契約詳細画面の契約明細一覧で確認してください。

### 会社の同一性判定（重複登録の防止）

CSVの再インポート時に同じ会社が重複登録されるのを防ぐため、会社の同一性は次の優先順位で判定します。

1. `Contract.externalId`（会社ID、CSVの`companyExternalId`列）が一致する
2. 会社IDが無い場合のみ、`companyName`（前後・連続する空白を正規化した上で）が完全一致する

会社名だけの判定は、CSVの表記ゆれ（全角/半角スペースの違い、改行の混入など）によって
同じ会社が別の契約先として重複登録されるリスクがあります。torimato側に顧客IDなど
会社単位で一意な列があれば、CSVインポート画面で必ず「会社ID」にマッピングしてください。
契約明細（`ContractLine`）は「最新CSVが正」の方針で毎回丸ごと置き換えるため、行単位の
同一性判定（過去の行との突合）は行いません（詳細は下記「CSVインポート方式」を参照）。

**契約ID（`ContractLine.externalId`）は会社の識別・`Contract`の作成や分割判定には
一切使用しません。** torimatoでは同じ顧客・同じ会社でも契約ごとに異なる契約IDを持つのが
正しい状態のため、契約IDを会社識別に使うと同じ会社が契約の数だけ複数の`Contract`に
分裂してしまいます。会社のグルーピングキーは会社ID（`companyExternalId`）または
会社名（`companyName`）のみで、契約IDはContractLineの参考情報として保存されるだけです。

例えば次のように、同じ顧客IDで契約IDだけが異なる複数行がある場合:

```
顧客ID: ABC123 / 契約ID: 001 / 月契約
顧客ID: ABC123 / 契約ID: 002 / 年契約
```

会社（`Contract`）は1件、契約明細（`ContractLine`）は2件として取り込まれます。

**同じ会社の行の一部だけに会社IDが入っている場合（他の行は空欄）でも、必ず1つの会社としてまとめます。**
torimatoのCSVでは、同じ会社の複数の契約明細のうち一部の行にだけ顧客IDが入っていることがあります。
これを単純に「行ごとに会社IDがあればID、無ければ会社名でグループ化」してしまうと、同じ会社の行が
「会社IDで判定されるグループ」と「会社名で判定されるグループ」に分かれてしまい、同じ会社が
複数の`Contract`に分裂したり、後から処理される方のグループが先に取り込んだ契約明細を
消してしまう（会社は1件に見えても中身が消える）事故につながります。そのため取り込み時は、
まずCSV全体から「その会社名のどこかの行が持っている会社ID」を1つ解決し、その会社名の
全ての行に同じ会社IDを適用してからグループ化します。また、会社IDでは既存の`Contract`が
見つからない場合（例: 以前は会社名だけで作られていた会社に、今回のCSVで初めて会社IDが
判明した場合）も、会社名でのフォールバック検索を行ってから新規作成するため、既存の
会社に正しく統合されます（新しい`Contract`を誤って作ってしまうことはありません）。

**「会社ID」と「契約ID」は列を間違えると重大な不具合につながるため、部分一致による
自動推測（他の項目のような「列名にこの文字列を含む」方式）は行いません。**
「顧客ID」「契約ID」など、torimatoの実際の列名として明確に分かっている名前と
**完全一致**する列名がある場合のみ自動マッピングします（下記「自動マッピングされる列名」参照）。
自動マッピングされた場合も、取り込み前に必ずCSVの中身を確認してください。

- 会社ID（`companyExternalId`）: 同じ会社の全ての行で**共通の値**になっている列（例: 顧客ID、取引先コード）
- 契約ID（`externalId`）: 契約明細1行だけを指す、**行ごとに異なる値**になっている列（例: 契約番号、明細ID）

自動マッピングされた列が実際には会社単位・行単位の一意な値になっていない場合や、
どの列が本当の顧客IDなのか確信が持てない場合は、マッピングを空欄に変更してください
（会社名だけで判定されます）。マッピングを誤ると（例えば契約ID列を会社IDに割り当てると）、
同じ会社が複数の契約先に分裂したり、逆に別々の会社の契約明細が誤って1社にまとまったりします。

これを防ぐため、CSVインポート画面には「会社ID」または「契約ID」がマッピングされている場合
（自動マッピング・手動マッピングいずれも）、CSV全行を検査して次のような矛盾を検出する
警告機能があります。

- 同じ会社名なのに、会社IDの値が行によって異なる → 契約IDや行番号などを誤って会社IDに
  マッピングしている可能性が高い
- 同じ契約IDが複数の会社名にまたがって出現する → 会社IDや別の列を誤って契約IDに
  マッピングしている可能性が高い

警告が出た場合はマッピングを見直してください。内容を確認した上でどうしても
そのまま取り込みたい場合のみ、確認チェックボックスにチェックを入れると取り込みできます。

### 自動マッピングされる列名

CSVの列名がtorimatoの実際の表記に近い場合、インポート画面で以下のように自動マッピングされます
（自動マッピングされた内容は、取り込み前にプルダウンで確認・変更できます）。

| torimatoのCSV列名（例） | システムの項目 | 判定方法 |
| --- | --- | --- |
| 顧客名 | `companyName`（会社名） | 部分一致 |
| 顧客ID | `companyExternalId`（会社ID） | **完全一致のみ** |
| サービス名 | `productName`（商品名） | 部分一致 |
| 数量 | `quantity`（数量） | 部分一致 |
| 金額(税込) | `amount`（金額） | 部分一致 |
| 契約期間（開始） | `startDate`（契約開始日） | 部分一致 |
| 契約期間（終了） | `endDate`（契約終了日） | 部分一致 |
| 申込日 | `applicationDate`（申込日） | 部分一致 |
| 代理店 | `agencyName`（代理店） | 部分一致 |
| 契約タイプ | `contractType`（契約種別） | 部分一致 |
| 契約状態 | `contractStatus`（契約状態） | 部分一致 |
| 請求方法 | `billingMethod`（請求方法） | 部分一致 |
| キー発行済み | `keyIssuedStatus`（キー発行状況） | 部分一致 |
| 契約ID | `externalId`（契約ID） | **完全一致のみ** |

「完全一致のみ」の2項目（会社ID・契約ID）は、`src/app/contracts/import/page.tsx`の
`EXACT_GUESS`に列挙した候補名（顧客ID/顧客CD/会社ID/取引先ID/取引先コード、
契約ID/契約番号/明細ID）と列名が完全一致する場合のみ自動マッピングされます。
他の項目は部分一致（`GUESS`、列名にキーワードを含むか）で判定するため、多少の表記ゆれ
（「金額(税込)」「契約期間（開始）」等）があっても認識できます。

### 未使用列（マッピングされていないCSV列）の確認

CSVを読み込むと、どのシステム項目にもマッピングされなかった列が「未使用列」として
一覧表示されます。CSVに新しい列が増えた場合や、まだこのシステムで使っていない項目に
気付くために利用してください。取り込み自体は未使用列があっても行えます（その列の内容は
単に保存されません）。

### 既に重複登録されたローカルDBの直し方

過去のバージョンで会社名の表記ゆれ等により同じ会社が複数の`Contract`として
重複登録されてしまった場合、`git pull`してこのバージョンのコードに更新するだけでは
**既存の重複データは自動的にはマージされません**（今回の修正は今後の重複を防ぐもので、
過去に作られてしまった重複行を後から統合する機能ではないため）。

開発環境のローカルDBであれば、次の手順でリセットしてから再インポートするのが
最も安全で簡単です。

```bash
git pull
npx prisma migrate reset   # ローカルDBを空の状態に戻し、全マイグレーションを再適用する
npm run seed               # 担当者・メールテンプレートの初期データを入れ直す（任意）
```

その後、CSVインポート画面から改めてCSVを取り込んでください。torimato側に顧客ID列が
あれば「会社ID」に必ずマッピングしてください（無い場合は会社名で判定されます）。

どうしても既存データ（対応履歴など）を残したい場合は、Prisma Studio（`npx prisma studio`）
で重複している`Contract`を確認し、残したい1件以外を手動で削除してから再インポートしてください
（`ContractLine`・`SupportLog`は`Contract`削除時に連動して削除されます）。ただし本番相当の
大事なデータでなければ、上記のリセットの方が確実です。

### インポート結果の検証スクリプト

CSVインポート後、データが正しく取り込まれているかをコマンドラインでまとめて確認できます。

```bash
npm run verify
```

現在のDB全体に対して次を検証し、結果を一覧表示します。

- 直近のインポート履歴（`ImportBatch`、最新5件: 日時・ファイル名・CSV行数・会社数・成功/エラー件数）
- 同一会社名（表記ゆれ正規化後）が複数の`Contract`に分裂していないか。分裂している場合は
  該当する会社名・各Contractの`id`/`externalId`/契約明細数と、考えられる原因（会社IDが
  行によって異なる、会社IDの有無が混在している、等）を表示
- `accountCount`（契約中の契約明細のquantity合計）が正しく計算されているか、アプリ本体とは
  別の独立したロジックで再計算してクロスチェック
- `contractStatus`が未設定（null）の契約明細が無いか（あれば集計から漏れている旨を表示）
- 契約ID（`ContractLine.externalId`）がDB全体で重複していないか
- **主要項目のマッピング網羅率**: `productName`・`contractType`・`contractStatus`・`amount`・
  `quantity`・`startDate`/`endDate`・`applicationDate`・`agencyName`・`billingMethod`・
  `keyIssuedStatus`それぞれの未設定件数と割合を表示。`productName`・`contractType`・
  `contractStatus`・`amount`のいずれかが50%以上未設定、または`quantity`が不正な場合は
  `[NG]`として表示（CSVインポート画面でその列がマッピングされているか確認する）
- 契約種別（`contractType`）の検証: 年契約/月契約/未設定それぞれの件数、
  商品名（`productName`）が「【年間プラン】」なのに`contractType`が「月契約」になっている件数、
  「【月額プラン】」なのに「年契約」になっている件数。不一致があれば会社名・商品名・契約種別・金額を一覧表示し、
  最後に`[OK] 契約種別`/`[NG] 契約種別`を出力
- 会社ごとのaccountCount・サポートプラン・契約明細数のサマリ一覧

同一CSVを2回取り込んでも`ContractLine`件数が増えないこと（再インポートの冪等性）は、
`npm run verify`の「会社数」「契約明細数」を再インポートの前後で見比べることで確認できます
（インポート結果に表示される「今回のCSVで◯件に置き換え」が毎回CSVの行数と一致していることでも確認できます）。

## CSVインポート方式（「最新のCSVが現在の契約状態の正」）

以前のバージョンは、契約ID（`externalId`）や契約種別・商品名・契約期間をキーに既存の
`ContractLine`と突き合わせて更新するupsert方式でした。しかしtorimatoの契約ID列は
再エクスポートのたびに値が変わることがあり、同一性判定に失敗して同じCSVを複数回
インポートするたびに`ContractLine`が増殖する不具合が繰り返し発生していました。

そのため、現在は次の単純な方式に変更しています。

1. CSVを解析し、行を会社単位（会社IDがあれば会社ID、無ければ正規化した会社名）でグループ化する
2. 会社ごとに`Contract`を作成・更新する（連絡先などは今回のCSVに値がある項目だけ上書き）
3. **その会社の既存`ContractLine`を全件削除し、今回のCSVの内容で作り直す**
   （過去の`ContractLine`との突合・upsertは一切行わない）
4. 会社単位でアカウント数（`contractStatus`が「契約中」の`quantity`合計）を再計算する

この方式により、契約IDが毎回変わっても、同じCSVを何度インポートしても`ContractLine`は
常に「そのCSVの行数」のままになります。数量や契約状態が前回と変わっていれば、
今回のCSVの値がそのまま反映されます（＝最新CSVが正）。

**Contract（会社そのもの）・`SupportLog`（対応履歴）・担当者・メールテンプレートは
CSV再インポートで削除されません。** 削除・置き換えの対象はあくまで会社に紐づく
`ContractLine`のみです。

過去にどのCSVを・いつ・何件取り込んだかという実行履歴は`ImportBatch`テーブルに残ります
（`npm run verify`の実行結果の先頭に直近5件が表示されます）。`ContractLine`自体は
最新CSVの内容に置き換わってしまうため、過去のCSVの中身そのものを復元することはできません。

### 再インポートの冪等性テスト手順

同じCSVを複数回インポートしても`ContractLine`が増殖しないことは、次の手順で確認できます。

```bash
git pull
npx prisma migrate reset   # ローカルDBを空の状態に戻し、全マイグレーションを再適用する
npm run seed               # 担当者・メールテンプレートの初期データを入れ直す（任意）
npm run dev
```

1. `/contracts/import` からCSVを1回目インポートする
2. `npm run verify` で会社数・契約明細数を確認する
3. 同じCSVをもう一度（2回目・3回目と）インポートする
4. 都度`npm run verify`を実行し、会社数・契約明細数が増えていないことを確認する
   （インポート結果の「今回のCSVで◯件に置き換え」も毎回CSVの行数と一致するはず）
5. 契約詳細画面やPrisma Studio（`npx prisma studio`）で、CSV再インポート前に記録した
   対応履歴（`SupportLog`）が消えずに残っていることを確認する
