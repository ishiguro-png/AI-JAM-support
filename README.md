# AI JAM サポート管理システム

admin.torimato.jp の契約管理システムから、サポートプラン対象（5アカウント以上 / 10アカウント以上 / 30アカウント以上）の契約先を抽出・管理するための社内ツールです。

- torimato からエクスポートしたCSVを取り込み、契約行の数量を会社単位で合算し、サポートプラン（5+ / 10+ / 30+）を自動判定
  （同一会社の「月契約」「年契約」等の複数行にも対応。「契約状態」列が「契約中」の行だけをカウントし、契約開始日・終了日は表示用にのみ保持）
- 契約先ごとにサポートメールをGmail経由で送信し、送信内容・送信結果を自動で対応履歴に記録
- 電話・訪問・メモなどメール以外の対応も手動で記録でき、誰が対応しても同じ画面で経緯が追える
- ログイン機能は設けず、社内アクセスのみを前提とした簡易システムです（担当者名は入力式で記録）

## 技術構成

- Next.js 14 (App Router) + TypeScript
- Prisma + SQLite（ファイルDB、`prisma/dev.db`）
- Tailwind CSS
- Nodemailer（Gmail SMTP、アプリパスワード方式）
- PapaParse（CSVパース、列マッピングはブラウザ上で実施）

## セットアップ

```bash
npm install
cp .env.example .env
# .env を編集: GMAIL_USER / GMAIL_APP_PASSWORD を設定
npx prisma migrate dev   # リポジトリに含まれるマイグレーションを適用（新規追加は不要なので --name は付けない）
npm run seed   # 担当者・メールテンプレートの初期データ投入（任意）
npm run dev
```

http://localhost:3000 で起動します。

### Gmail送信の設定

サポートメールは実際にGmail経由で送信されます。送信専用のGoogleアカウント（または担当部署のアカウント）で以下を行ってください。

1. Googleアカウントで2段階認証を有効化
2. https://myaccount.google.com/apppasswords でアプリパスワードを発行
3. `.env` の `GMAIL_USER` に送信元アドレス、`GMAIL_APP_PASSWORD` に発行されたアプリパスワードを設定

## 使い方

1. **CSVインポート**（`/contracts/import`）: torimatoからエクスポートしたCSVをアップロードし、列とシステム項目（会社名・会社ID・数量・契約状態・契約種別・契約開始日・契約終了日・商品名・金額・契約IDなど）を対応付けて取り込みます。
   会社名・数量・契約状態は集計に必須のためバリデーションされます。会社ID・契約ID・契約種別・契約開始日・契約終了日は任意項目です。
   torimatoのCSVは同一会社について「月契約」「年契約」が別行になっていることがありますが、1行 = 1つの契約明細として取り込まれ、会社単位でまとめられます。
   会社の同一性は「会社ID」があればそれを優先し、無ければ会社名で判定します。会社名だけの判定は全角/半角スペースなどの表記ゆれで
   同じ会社が別の契約先として重複登録される恐れがあるため、torimato側に顧客IDなど会社単位で一意な列があれば必ずマッピングしてください。
   契約明細（行）の同一性も同様に「契約ID」があればそれを優先します。一致した既存契約には契約明細が追加/更新され、連絡先などの情報も上書き更新されます。
2. **契約一覧**（`/contracts`）: サポートプラン（5+/10+/30+）やステータスで絞り込み、対象契約先を確認できます。
3. **契約詳細**（`/contracts/[id]`）: 契約先ごとに現在のアカウント数の内訳（契約明細一覧。各行の契約状態が「契約中」なら集計対象、それ以外は対象外）、サポートメールの送信、対応履歴（電話・訪問・メモ等）の記録・閲覧ができます。
4. **メールテンプレート**（`/templates`）: プラン別の定型連絡文をあらかじめ登録し、送信フォームから呼び出せます。
5. **担当者管理**（`/staff`）: 対応記録・メール送信時に選択する担当者名を管理します。

## データモデル

- `Contract`: 契約先（会社）情報。会社名・会社ID（任意、torimatoの顧客IDなど）・連絡先・ステータス。アカウント数とサポートプランはここには保存せず、`ContractLine`から都度集計する
- `ContractLine`: 契約明細（torimatoの1行 = 月契約/年契約などの単位）。契約種別・契約状態・数量・契約開始日・契約終了日・商品名・金額を保持
  （商品名・金額は表示用・`npm run verify`の整合性チェック用で、集計には使用しない）
- `SupportLog`: 対応履歴（メール送信ログを含む。種別・担当者・内容・日時）
- `EmailTemplate`: プラン別メールテンプレート
- `Staff`: 対応記録用の担当者名リスト

### アカウント数の集計ロジック

会社ごとに、**`ContractLine.contractStatus`（契約状態）が「契約中」の行のみ**を対象に数量を合算し、
その合計値でサポートプラン（5+/10+/30+）を判定します。「契約前」「解約」の行はカウントに含みません。

torimatoのCSVに入っている契約開始日・契約終了日は、無料期間や契約切り替えの都合で実際の契約状態と
ずれることがあるため、**集計判定には一切使用せず**、契約詳細画面に表示する参考情報としてのみ保持します。
このため`ContractLine.startDate`/`endDate`は任意項目（無くても取り込み可能）です。

集計はページ表示のたびに計算されるため、CSVの契約状態を更新して再インポートすれば、
即座に一覧・ダッシュボードのアカウント数・プラン判定に反映されます。

### `Contract.status` と `ContractLine.contractStatus` は別物

- `Contract.status`（稼働中/一時停止/解約）: このアプリ内だけで管理する対応ステータス。契約詳細画面から手動で変更する。**CSVインポートで書き込まれることはない**
- `ContractLine.contractStatus`（契約中/契約前/解約）: torimatoのCSVの「契約状態」列そのもの。契約明細（行）ごとに保持し、アカウント数集計にのみ使う

会社は複数の契約明細を持ちうる（例: 月契約=契約中、年契約=契約前）ため、契約一覧画面では
個々の契約明細のcontractStatusをそのまま会社の行に表示せず、「有効N / 全M件」という
会社単位の集約表示にしています。契約状態の内訳は契約詳細画面の契約明細一覧で確認してください。

### 会社の同一性判定（重複登録の防止）

CSVの再インポート時に同じ会社が重複登録されるのを防ぐため、会社の同一性は次の優先順位で判定します。

1. `Contract.externalId`（会社ID、CSVの`companyExternalId`列）が一致する
2. 会社IDが無い場合のみ、`companyName`（前後・連続する空白を正規化した上で）が完全一致する

会社名だけの判定は、CSVの表記ゆれ（全角/半角スペースの違い、改行の混入など）によって
同じ会社が別の契約先として重複登録されるリスクがあります。torimato側に顧客IDなど
会社単位で一意な列があれば、CSVインポート画面で必ず「会社ID」にマッピングしてください。
契約明細（行）についても同様に、`ContractLine.externalId`（契約ID）があればそれを
同一性判定に使い、無い場合のみ契約種別・契約開始日・契約終了日の組で判定します
（開始日・終了日の両方が揃っている場合のみ）。

**「会社ID」と「契約ID」は列を間違えると重大な不具合につながるため、自動推測は一切行いません。**
必ずCSVの中身を見て、人が判断してマッピングしてください。

- 会社ID（`companyExternalId`）: 同じ会社の全ての行で**共通の値**になっている列（例: 顧客ID、取引先コード）
- 契約ID（`externalId`）: 契約明細1行だけを指す、**行ごとに異なる値**になっている列（例: 契約番号、明細ID）

どの列が本当の顧客IDなのか実際のCSVを見ても確信が持てない場合は、無理にマッピングせず
「会社ID」を空欄のまま取り込んでください（会社名だけで判定されます）。マッピングを誤ると
（例えば契約ID列を会社IDに割り当てると）、同じ会社が複数の契約先に分裂したり、
逆に別々の会社の契約明細が誤って1社にまとまったりします。

これを防ぐため、CSVインポート画面には「会社ID」または「契約ID」をマッピングした際に、
CSV全行を検査して次のような矛盾を検出する警告機能があります。

- 同じ会社名なのに、会社IDの値が行によって異なる → 契約IDや行番号などを誤って会社IDに
  マッピングしている可能性が高い
- 同じ契約IDが複数の会社名にまたがって出現する → 会社IDや別の列を誤って契約IDに
  マッピングしている可能性が高い

警告が出た場合はマッピングを見直してください。内容を確認した上でどうしても
そのまま取り込みたい場合のみ、確認チェックボックスにチェックを入れると取り込みできます。

### 既に重複登録されたローカルDBの直し方

過去のバージョンで会社名の表記ゆれ等により同じ会社が複数の`Contract`として
重複登録されてしまった場合、`git pull`してこのバージョンのコードに更新するだけでは
**既存の重複データは自動的にはマージされません**（今回の修正は今後の重複を防ぐもので、
過去に作られてしまった重複行を後から統合する機能ではないため）。

開発環境のローカルDBであれば、次の手順でリセットしてから再インポートするのが
最も安全で簡単です。

```bash
git pull
npx prisma migrate reset   # ローカルDBを空の状態に戻し、全マイグレーションを再適用する
npm run seed               # 担当者・メールテンプレートの初期データを入れ直す（任意）
```

その後、CSVインポート画面から改めてCSVを取り込んでください。torimato側に顧客ID列が
あれば「会社ID」に必ずマッピングしてください（無い場合は会社名で判定されます）。

どうしても既存データ（対応履歴など）を残したい場合は、Prisma Studio（`npx prisma studio`）
で重複している`Contract`を確認し、残したい1件以外を手動で削除してから再インポートしてください
（`ContractLine`・`SupportLog`は`Contract`削除時に連動して削除されます）。ただし本番相当の
大事なデータでなければ、上記のリセットの方が確実です。

### インポート結果の検証スクリプト

CSVインポート後、データが正しく取り込まれているかをコマンドラインでまとめて確認できます。

```bash
npm run verify
```

現在のDB全体に対して次を検証し、結果を一覧表示します。

- 同一会社名（表記ゆれ正規化後）が複数の`Contract`に分裂していないか。分裂している場合は
  該当する会社名・各Contractの`id`/`externalId`/契約明細数と、考えられる原因（会社IDが
  行によって異なる、会社IDの有無が混在している、等）を表示
- `accountCount`（契約中の契約明細のquantity合計）が正しく計算されているか、アプリ本体とは
  別の独立したロジックで再計算してクロスチェック
- `contractStatus`が未設定（null）の契約明細が無いか（あれば集計から漏れている旨を表示）
- 契約ID（`ContractLine.externalId`）がDB全体で重複していないか
- 同一会社内で`externalId`以外の全項目（契約種別・商品名・数量・契約状態・金額・契約期間）が
  完全に一致する契約明細が複数存在しないか（＝`externalId`だけが異なる「内容重複」。
  CSVを再エクスポートするたびに契約IDの値が変わってしまう場合に典型的に発生する）
- 契約種別・契約開始日・契約終了日・商品名が軒並み未設定の契約明細が大量にある場合、
  CSVインポート画面でこれらの列のマッピングを忘れている可能性を警告
- 契約種別（`contractType`）の検証: 年契約/月契約/未設定それぞれの件数、
  商品名（`productName`）が「【年間プラン】」なのに`contractType`が「月契約」になっている件数、
  「【月額プラン】」なのに「年契約」になっている件数。不一致があれば会社名・商品名・契約種別・金額を一覧表示し、
  最後に`[OK] 契約種別`/`[NG] 契約種別`を出力
- 会社ごとのaccountCount・サポートプラン・契約明細数のサマリ一覧

同一CSVを2回取り込んでも件数が増えないこと（再インポートの冪等性）は、
`npm run verify`の「会社数」「契約明細数」を再インポートの前後で見比べることで確認できます
（インポート結果に表示される「新規◯件/更新◯件」が2回目は「新規0件」になっていることでも確認できます）。

### 契約明細の同一性判定（契約IDだけに依存しない）

CSVの「契約ID」列は、torimatoの再エクスポートのたびに値が変わってしまうことがあります
（＝本来の意味での安定した一意キーではない）。契約IDだけで同一性を判定すると、契約IDが
毎回変わるたびに「既存の明細が見つからない」と判定され、同じ契約明細が再インポートの
たびに新規作成され続けてしまいます。

これを防ぐため、契約明細の同一性は次の優先順位で判定します。

1. 契約ID（`externalId`）が一致する明細
2. 見つからない場合、同じ会社の中で**契約種別・商品名・契約開始日・契約終了日**
   （＝時間が経っても変わらないはずの識別情報）が完全に一致する明細
   （商品名・契約期間の両方が未設定だと識別力が弱すぎるため、その場合はフォールバックせず新規作成する）

数量・契約状態・金額はこの同一性判定には使いません（時間経過で正しく変わりうる値のため、
含めてしまうと"契約前→契約中"のような状態遷移のたびに別明細として重複作成されてしまいます）。

**重要**: 契約種別・商品名・契約開始日・契約終了日は必須項目ではないため、CSVインポート画面で
これらの列をマッピングし忘れても取り込み自体はエラーになりません。しかし全てマッピングしないと
上記2の照合ができなくなり、契約IDが不安定な場合に再インポートのたびに増殖してしまいます。
**商品名または契約開始日・終了日のどちらかは必ずマッピングすることを強く推奨します。**
`npm run verify`はこれらが軒並み未設定の場合に警告を表示します。

### 契約明細の内容重複を整理するスクリプト

`npm run verify`で「内容重複」が検出された場合、次のコマンドで整理できます。

```bash
npm run dedupe-lines            # 削除対象を表示するだけ（何も削除しない・安全）
npm run dedupe-lines -- --apply # 実際に削除する
```

同一Contract配下で、契約種別・商品名・数量・契約状態・金額・契約開始日・契約終了日
（`externalId`以外の全項目）が完全に一致する契約明細をグループ化し、各グループで最も
更新日時（`updatedAt`）が新しい1件だけを残して残りを削除します（＝直近のCSVインポートで
反映された最新の状態を優先します）。全項目が完全一致する場合のみ同一とみなすため、
状態が進んだ明細（例: 契約前→契約中に変わった明細）まで誤って削除することはありません。

契約種別・商品名・契約期間が全て未設定のグループは、数量・契約状態・金額だけで一致判定する
ことになり偶然の一致が起きやすいため「信頼度: 低」と表示されます。`--apply`前に内容を
よく確認してください。

**契約種別・商品名・契約期間が全て未設定のまま重複が起きている場合**（＝上記フィールドの
どれもマッピングされていない場合）は、`dedupe-lines`で整理した後も、同じCSVを
マッピング未修正のまま再インポートすると再び増殖します。必ず先に商品名または
契約開始日・終了日をマッピングするよう修正してから再インポートしてください。
